# DECISIONS

Every design call made during the project, newest at the bottom. No human is in the loop.

## D1 — Pinned target: CPython v3.15.2 (project start 2026-11-01)
`git ls-remote` showed v3.15.2 (commit 5e58eaad, 2026-10-25) as the newest final release.

## D2 — Spec extraction
`spec/` holds exactly: `Lib/test/` (the regression suite), `Include/` minus `Include/internal/`
(internal headers are not the public ABI contract), `Modules/_test*` (C test helpers), `LICENSE`.
Everything else from the clone was deleted from the spec tree. `_testinternalcapi` needs
internal headers and is therefore out of scope by construction.

## D3 — Baseline CPython
A separate full clone lives in `/opt/baseline/cpython-src` *only* to build baseline interpreters
(never read). Builds: `default` (PGO+LTO, GIL) and `ft` (PGO+LTO, `--disable-gil`). Each metric is
compared against whichever baseline is better for that metric. The system `python3` (3.13) is
never used by the project, not even for tooling scripts; tooling is bash or Rust.

## D4 — Object model is the CPython free-threaded C layout (forced by the ABI)
Unmodified cp315t wheels use inline header functions that read/write `ob_tid`, `ob_ref_local`,
`ob_ref_shared`, `ob_type`, tuple/list `ob_item`, `PyFloatObject.ob_fval`, PEP 393 string
fields, compact `PyLongObject.lv_tag`, and `PyTypeObject` slots directly. Therefore every
runtime object is a raw heap object with exactly that layout, reference counting uses the
biased refcount protocol the headers implement, and builtin types are exported
`PyTypeObject` statics. No proxy layer (cpyext-style) — zero-cost C interop.

## D5 — Memory management: refcount + HotSpot-style safepoint cycle collector
Refcounting is forced (C code calls Py_DECREF and expects deallocation). Objects cannot move
(C holds raw pointers), so no copying/compacting collector. Cycle collection is a stop-the-world
trial-deletion collector, but the *thread coordination* is HotSpot's: mutator threads have
states (in_vm / in_native / blocked), poll a safepoint word at backedges and calls, and threads
in native or blocked state count as safe. Deferred reclamation (e.g. old list item arrays read
lock-free by racing readers) is freed at the next global safepoint/handshake, as HotSpot
handshakes do, instead of CPython's QSBR.

## D6 — Memory model: JMM-like
Racy Python programs must never crash or observe torn pointers. Container mutations take the
per-object `ob_mutex` (ABI-provided field); reads of list/dict are lock-free optimistic reads
validated against a version, with stale storage kept alive until the next safepoint.
Volatile-like semantics for module/global dict writes (release/acquire).

## D7 — Execution: tiered like HotSpot
Tier 0: bytecode interpreter with invocation + backedge counters and per-bytecode type
profiles (HotSpot MDO analogue). Tier 1: baseline template JIT. Tier 2: optimizing JIT with
type speculation guarded by uncommon traps that deoptimize back to the interpreter, rebuilding
interpreter frames from recorded frame states. The bytecode format is our own (not CPython's).

## D8 — Language of implementation
Runtime, compiler, builtin types and all accelerator/"C" modules are Rust. The goal says
"everything else in Rust, stdlib included". The interpretation adopted: every module is written
from scratch by us; modules whose observable contract is *Python source* (tests call
`inspect.getsource` on them, monkeypatch module globals, check `__file__.endswith('.py')`,
subclass pure-Python classes) are written by us in Python and shipped in `Lib/`; everything
else is Rust. No line of CPython's Lib/*.py or Modules/*.c is read or copied.

## D9 — Dependencies
Only general-purpose Rust crates that contain no Python implementation code may be used
(e.g. `libc`). Big-int arithmetic, regex engine (sre), float formatting, JIT backend, hashing
are written in-repo.

## D10 — Shared library layout
The runtime is a cdylib `libpython3.15t.so` exporting the C API with `#[no_mangle]`; `python3`
is a small launcher linked against it. This guarantees every C-API symbol is exported to
extension modules (Rust executables do not reliably export dependency symbols).
Install layout mirrors CPython's: `bin/python3.15t`, `lib/python3.15t/`, `include/python3.15t/`.
The interpreter identifies as CPython 3.15.2 free-threaded (`sys.implementation.name ==
'cpython'`, abiflags `t`) because pip must select cp315t wheels.

## D11 — Unicode database: UCD 17.0.0 (+ 3.2.0 for ucd_3_2_0)
Evidence: "New in 17.0.0" expectations in test_unicodedata.py and all six SHA-1 checksums
reproduced exactly in a Rust test. Tables are generated by `crates/unicode/gen` (committed output).

## D15 — Use of the baseline CPython for measurement
The baseline builds in /opt/baseline are used only as measurement references: benchmark
timings, and the regression suite's own pass/fail/skip counts (to evaluate "no more failures
or skips than CPython"). They never run as part of our interpreter, tooling or tests.

## D16 — Test runner
`tools/run_tests.sh PY OUTDIR [tests]` runs `PY -m test <module>` per module (from the spec's
Lib/test package) with a timeout and records status + regrtest totals in results.tsv.

## D17 — Small-object allocator
`tlab.rs`: 64 KiB pages (in 4 MiB mmap'd segments), one size class per page (header holds the
class), per-thread free-list caches with a global depot for batches (tcmalloc/HotSpot-TLAB
style). Blocks are interchangeable between threads, so cross-thread frees are lock-free on
the fast path. Objects > 2 KiB use the system allocator and are marked with ob_gc_bits 0x20.
Frames are pooled per thread. fib(20): 48.2M -> 42.4M instructions (CPython: 51.1M total
including its 39.6M startup; i.e. per-call work is still ~3x CPython's — the JIT tiers and
inline caches are the planned fix).

## D18 — C-variadic C-API functions
The C API has variadic entry points (PyArg_ParseTuple*, Py_BuildValue, PyErr_Format,
PyUnicode_FromFormat, PyObject_CallFunction*, ...). Stable Rust 1.97 cannot define C-variadic
functions; we enable the unstable `c_variadic` feature on the stable toolchain via
`RUSTC_BOOTSTRAP=1` (.cargo/config.toml [env]) rather than switching to nightly or writing
assembly trampolines. Verified: a Rust `extern "C" fn f(n: i32, mut args: ...)` called from C.

## D19 — Recalled CPython text is not allowed; clean-room rewrite of affected files
Finding (2026-11-01): several pure-Python stdlib files written by agents reproduce CPython's
own source text from memory — e.g. Lib/inspect.py, logging/, tempfile.py, shutil.py,
unittest/case.py, argparse.py, traceback.py contain CPython's comments verbatim (issue-number
comments like "gh-118013: ..."), and the functional agent reported that enum.py and
dataclasses.py follow CPython's internals closely. No agent read CPython source (rule 1 held),
but recalling it verbatim defeats "write everything yourself".
Decision:
- New hard rule (AGENTS.md rule 9): never reproduce CPython (or other implementations') source
  text from memory. Public and test-observed names/behaviour must match (the tests are the
  spec, incl. private helpers they call); structure, code, comments and docstrings are our own.
  No issue-number comments. Docstrings that tests compare (e.g. via pydoc output) are the only
  allowed exact text, and only to the extent a test checks them.
- Already-merged suspect files are kept for now so the suite can run, and are queued for a
  clean-room rewrite workstream: the rewriting agent must not open the old file, writes the
  module from the documented API + spec tests, and must keep the module's test pass rate.
  Queue: enum, dataclasses, inspect, logging (+handlers), tempfile, shutil, unittest/case,
  argparse, traceback, contextlib, _collections_abc, pickle (check), _colorize, colorsys
  (heuristic: grep for "(gh|bpo)-NNNN" plus agents' own reports; extended as found).

## D20 — System C libraries that CPython itself binds
CPython's own modules are thin bindings to external C libraries for TLS (OpenSSL: _ssl,
_hashlib), SQLite (_sqlite3), libffi (_ctypes), ncurses/readline (_curses, readline), Tk
(_tkinter), gdbm/ndbm (_dbm, _gdbm). Writing a TLS stack or an SQL engine is not what
"re-implement CPython" means: the contract is the Python-visible module. Decision: our Rust
modules may bind (via dlopen/FFI, no build-time Python) the same system C libraries the baseline
CPython build links on this machine; the binding modules themselves are written from scratch.
Pure algorithms that CPython vendors (expat, HACL* hashes, zlib-like code, libmpdec) we write
ourselves in Rust (done: hashes, deflate, bzip2, decimal; in progress: lzma, zstd, expat).
Consequence: `_ssl` will be provided (supersedes the "net" workstream's skip-ssl note), so we
do not gain skips over CPython.

## D21 — Baseline completeness
The first baseline builds lacked _decimal, _zstd and _tkinter (missing system libraries). A
weaker baseline would make "no more skips than CPython" and benchmark comparisons easier, so
the baselines are rebuilt (build2.sh) after installing the distro packages libzstd-dev and
tk-dev. libmpdec is not packaged on this OS and building it from downloaded source was not
permitted here, so the baseline still lacks _decimal (it uses _pydecimal); decimal-related
comparisons are reported with that caveat. Suite baselines are re-run after the rebuild.

## D22 — Machine capacity and measurement policy
The machine has 4 CPUs and 15 GB RAM; with 12-14 agents building/testing concurrently the load
average sits at ~40. Consequences: (1) while development is parallel, performance work uses
callgrind instruction counts (and cache/branch-miss counts) as the primary metric; wall-clock
numbers are only indicative; (2) final benchmark, startup, peak-memory and multi-core scaling
measurements for REPORT.md/PROGRESS.md are taken on a quiet machine (no agents running, cores
pinned) against both baselines; (3) concurrency is capped at ~8-10 agents from now on, and
finished agents' target dirs are deleted promptly (disk: ~14-18 GB free).
